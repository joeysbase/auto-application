# Parse stage (C6) — 2026-09-30
**Step:** 1   **Status:** done

## What
- `CommonPosting` (`core/models.py`): one shape for every source — title, company, locations, workplace/employment type, seniority, salary `{min, max, currency, period, text, source, plausible}`, posted date + precision, reposted, applicants, apply URL/kind, req id, description (text + HTML), extras.
- Parser interface: each plugin implements `parse(raw: RawPosting) -> CommonPosting` and declares `parser_version`. `RawPosting` carries everything saved for a posting (page text/HTML/JSON for browser sources; record + detail for API sources) plus the company's configured display name. Default for browser plugins: schema.org `JobPosting` JSON-LD.
- Parsers: **LinkedIn** (from visible page text, anchored on stable text, not generated class names), **Ashby** (structured salary), **Greenhouse** (entity-escaped HTML, `Location Type` metadata, requisition id), **Lever** (description + lists + additional), **Workday** (detail record; salary from the description's "N USD - N USD"; workplace from `#LI-Hybrid`-style tags).
- Shared helpers (`sources/common/text.py`): HTML → text, salary parsing ($K/yr, $/hr, "N USD - N USD", "per year"), relative dates, workplace/employment vocabularies.
- Stage (`process/parse.py`) + `auto-app parse [-s] [-c] [--reparse]`: `fetched → parsed | parse_failed`, `parsed.json` next to the raw files; skips postings already parsed by the same parser version, retries failures; prints field coverage per source. `inspect <source> <id>` shows the parsed fields.

## Findings
- LinkedIn's "… more" is only the expand button; the page text holds the full description.
- Workday's `hiringOrganization` is the legal entity ("2100 NVIDIA USA"); the configured display name is used instead and the entity kept in `extras`. (`display_name` added to the three companies in the config.)
- Changing a parser without bumping `parser_version` leaves old results in place — the version is what triggers re-parsing.
